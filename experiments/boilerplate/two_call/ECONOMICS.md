# Proposed C++ brick economics experiment

Status: design only. Freeze source revisions, cases, prompts, budgets and pricing assumptions before running. The B04–B06 line counter is a development case. It demonstrated a working replay and exposed two confounders: little requested behavior existed before editing, and returning 15 edits took more bytes than returning the four changed files. Keep it for harness checks.

## 1. Measure the value of a known match

Screen the existing USB inventory for two independently sourced C++ components in different feature families. A qualifying component must render from the frozen upstream source, have a documented interface, compile in a clean host, and pass an independent check for an externally observable feature before an LLM edits it. Record screening and packaging time, including rejections. Empty tests and counts of generated lines do not qualify. If the collection yields one qualifying family, report a one-family exploratory result. If none qualify, record a supply limitation and stop before model calls. No bespoke implementation of the benchmark feature may be added to the component.

For each family write two requests: a small program using the feature, and an extension that retains that same feature and adds a separately testable interaction. Define scope by requirements, not output LOC. For example, if an acquired Qt template is verified to provide a working item model, a small request could exercise the verified model operations and a larger one could integrate the same operations with a view and a new action. Whether that template qualifies requires inspection. Freeze external feature, integration and failure cases, fixtures and applicable structural checks. Keep them out of prompts and labels. Feature-matched requests test favorable conditions; they do not estimate how often users bring those requests.

| Arm | Workflow | Purpose |
| --- | --- | --- |
| A. Direct | English to a finished C++ project in one call. | Price the strongest simple baseline, including normal use of installed libraries and public framework APIs. |
| B. Scaffolding | English to spec, deterministic placement of a buildable project shell, editor finishes the task. | Measure the cost of a second call and working inside a project. |
| C. Working component | Same spec and shell as B, plus the verified component and its interface. The editor may use, change or discard it. | C versus B estimates the incremental value of the component. C versus A measures whether that value pays for the whole workflow. |

Preselect component IDs for C and document the match. Use the same general-purpose placement rules for both scopes; no custom glue implementing request behavior in the assembler. Run the external checks on the pre-edit assembly and again on the result. Separately record which features pass in an isolated component harness and in the assembled executable. A successful component may still be expensive to integrate.

Use the same model/version, reasoning setting, toolchain, dependency access, cache policy, wall-time and total per-request budget in all arms. Give every arm the same file creation and modification operations, including whole changed files and compact edits. Permit interface-first inspection and meter additional source reads. The B06 range-only editor needs file creation and whole-file replacement support before this comparison; validate the common tooling on development cases. No route gets free debugging output. Score first answers, then optionally allow the same one-repair policy using public build diagnostics for every route. Keep acceptance tests hidden and charge every attempt.

Start with two families × two scopes × three arms × three fresh repetitions = 36 scored runs. Within each task/repetition use one frozen interpreter response for B and C, charging its full usage to each route as it would incur in deployment. Randomize execution order within those constraints. Retain individual results and group by task and family. Three model repetitions measure run variability; they do not turn four tasks into twelve independent tasks. Treat small or inconsistent differences as inconclusive.

## 2. Measure the value on actual demand

Only advance if a working-component route produces comparable correct completions and a material cost advantage over direct generation in the favorable test. Before tuning, reserve at least twelve independent C++ requests from a defined source, ideally consecutive eligible requests from intended users or backlog. Exclude development cases and near duplicates. Pick these without consulting the catalog. If a representative source is unavailable, label the result a scenario study and leave the real hit rate open.

Freeze the catalog and automated picker's fallback policy. Compare A against the actual picker and editor on every request under the same budgets. Record usable hits, wrong placements, misses, direct fallbacks and all interpretation, retrieval, local compute, editing and repair costs. If fallback happens after the spec call, charge that call. Freezing the picker enables attribution; a diagnostic replay with a known match can distinguish retrieval failures from expensive integration. To test catalog size later, rerun the same requests with nested, independently frozen catalogs and the same picker. Record changes in hits, wrong placements and total cost.

## Accounting and decision

- A correct completion builds and passes all independently frozen mandatory checks. Report the completion fraction, per-task paired wins and losses, total spend across **all** requests divided by correct completions, mean cost per incoming request, and elapsed time. With zero correct completions report the spend and zero successes. Show first-pass and allowed-repair results separately.
- Keep uncached input, cached input, cache writes if applicable, and output separate. Reasoning is already included in output. Save model usage events and report both token counts and cost at a frozen rate schedule or stated internal valuation. Include local retrieval/build compute on the same basis across routes. If no meaningful dollar rate is available, publish the token vector and break-even sensitivity. Record the hours and compute to acquire, license-review, label, verify, index and maintain the catalog separately from per-request cost.
- Before running, choose a material saving threshold and acceptable quality/latency tradeoff. Suggested pilot gate: at least 20% lower cost per correct completion, no lower completion count, and savings across both feature families in stage 1. This is a proposed investment hurdle. A favorable small sample supports replication. If costs improve only in the feature-matched test, restrict the claim to that setting.
- For the deployment decision, let **D** and **P** be mean direct and pipeline cost per incoming request on the demand sample, including failed and fallback attempts. At comparable quality, expected net saving over **N** requests is **N × (D − P) − F**, where **F** includes setup and maintenance over that horizon. When **D > P**, break-even volume is **F / (D − P)**. If **D ≤ P**, increasing volume will not recover the fixed investment at those measured rates. Use plausible volume and hit-rate ranges when demand is uncertain.
