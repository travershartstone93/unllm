# C++ boilerplate picker pilot

The integrated converter pilot takes an English request. OpenCode uses Big Pickle first, then Iceman and the other hosted free models for English interpretation. When those attempts fail and OpenCode reports a quota error, the runner tries OVHcloud and then AI Horde. The [Arch pilot](../experiments/boilerplate/arch/README.md) searches official Arch and AUR metadata for a whole program, then tests eligible official candidates. When none passes, the deterministic picker assigns bricks. Unassigned outputs can use a unique compatible converter adapter or go through component selection and planning. A C++ assembler binds parameters and smaller providers, then the runner compiles and tests the program. Passing all requested checks with every role filled completes the run. Remaining failures or unresolved roles trigger a focused edit through the same provider order and another build and test. [Integrated runner and usage](../experiments/boilerplate/integrated/README.md) · [B21 results for both converters](/run/media/whisper/UNLLM_CORPUS/unllm/experiments/boilerplate-B21/README.md)

The B30 pilot has a 100-card catalog and can emit multi-operation CLIs and a single-header C++ queue class. On the six original requests replayed with fixed interpretations, all six generated programs passed their independent checks on the first build. Two still had outstanding English obligations. A perfect component-picker diagnostic recovered zero additional programs. [Staged results and limitations](EXPERIMENT_LOG.md#b30-verified-c-brick-library-and-staged-pipeline-upgrades)

## Implementation plan for the current collection

The immediate question is whether placing existing C++ bricks saves model work on a program that passes independent tests. Use the two frozen USB surveys (439 candidates, including 79 file or project scaffolds) and the one previously verified namespace/header pair. The 5,000-brick goal belongs to later corpus expansion. GitHub mining and the repository discovery queue follow the pilot evaluation.

Build an independently invocable C++ pilot in the existing upgrade checkout. Reuse the native encoder, available retrieval code and process runner where their interfaces fit. The current sandbox runner accepts a completed executable and mounts the project read-only. Give CMake a separate writable build directory during compilation. Keep provider selection configurable. OpenCode with Big Pickle is the first provider. The earlier Python replay demonstrates the invocation and is specific to another experiment.

### First end-to-end request

“Build a C++ command-line program that counts nonblank lines in a file. Put the counting logic in its own source file and include unit tests. A line containing only spaces or tabs is blank. Report an error if the file cannot be opened.”

The first candidates above have identifiable jobs here. The CMake project supplies an executable, the namespace pair supplies a separate compilation unit, the file-reader snippet is eligible for input, and the Google Test template supplies test declarations. The assembler registers sources and connects build targets. The editor can implement the counting rule, bind the path, add missing error behavior and write assertions. Check empty and whitespace-only files, mixed lines, an unterminated final line and a missing path from outside the generated tests. Also check that the separate source is actually linked and the requested unit tests fail under a deliberately wrong counting rule. Report the reader as missing if it cannot be placed correctly. Keep this request in development.

### Decision to expand

After B06, use the [brick economics experiment](../archive/boilerplate/two_call/ECONOMICS.md) for the next investment decision. It pairs direct generation, scaffolding and a verified component on the same tasks, then measures the actual picker on independently sampled demand if the favorable case pays. The original six-request smoke comparison below remains a development check.

Before tuning the picker, reserve six further requests as a pilot-sized comparison. Include a different composition, paraphrased requests, plausible incompatible matches, and a case with a genuine catalog gap. Set the expected behavior and acceptable alternatives independently of brick IDs. Use identical task wording, toolchain, acceptance checks and total budgets for the direct and assembled routes. Record model input and output separately, including both Big Pickle passes, editor context, retries and any model picker. Report correct completions and paired token and latency differences for tasks both routes solve. A timeout or an incorrect program stays in the completion tally.

Advance to a larger replication if the assembled route matches or exceeds direct generation on correct completions and uses fewer median total model tokens on paired successes. Report which projects benefited, where useful code survived the edit and whether extra latency offsets the saving. A single paired success is insufficient to judge savings. If the comparison is inconclusive, report that outcome. If the pipeline falls short, use the first failing stage to decide whether to improve catalog coverage, selection, assembly or editing before increasing corpus size.

## Assembly and repair checks

Record each brick's required inputs, results, side effects, headers and direct build dependencies in its assembly contract. Rebuild from those declared dependencies and run a behavioral test before treating it as verified. For image exporters, include a color input and check the decoded output pixels. B16 produced correctly named JPEGs with incorrect colors and returned success.

Before requesting a model edit, try composing a missing input or callback from compatible smaller bricks and build the emitted project. Retain its generated source, dependencies, diagnostics and test results. Where the compiler supplies a structured fix-it, try it in a separate build and rerun the same tests. For unresolved failures, give the editor the failing check, relevant source range and observed diagnostic, request a range patch, then recompile and rerun the external checks. Expand the context when the evidence spans more files. Record inference costs and any human-supplied diagnosis. [Focused repair results](/run/media/whisper/UNLLM_CORPUS/unllm/experiments/boilerplate-B18/README.md)

Score a run from hand-supplied roles separately from an ordinary English request. B19 exercises typed assembly and compiler feedback. The next generalization check should freeze the catalog and try a previously unseen combination of its capabilities, including a missing-capability control. ## Labeling and indexing

Each entry gets a short search description and a separate assembly contract. Start with the upstream description, descriptors, placeholders, imports and build files. Verify claims about behavior by instantiating and exercising the brick with at least two parameter sets in the appropriate harness.

| Field group | Example for a candidate parameterized test brick |
| --- | --- |
| Search description | “Define a Google Test case that runs against supplied parameter values.” Include aliases such as “table-driven test” only when supported. |
| Identity and environment | Stable ID and revision, C++ standard, framework/version, required headers, libraries and build targets. |
| Placement and connections | Test translation-unit scope. Requires a compatible fixture. Binds suite and case identifiers and opens an assertion-body slot. Record any separate instantiation requirement. |
| Evidence | Source revision and license, named template files, rendering inputs, build/run results and observed limitations. |

The picker’s example input for that role is `{"role":"test","behavior":"exercise the conversion on several input values","framework":"Google Test","constraint":"parameterized"}`. Big Pickle supplies the behavior and constraints. Catalog IDs and expected solutions stay out of this first pass.

Embed a short card per independently placeable capability, keyed to its brick ID. Use the installed, untuned BGE-small-en-v1.5 encoder, normalized 384-dimensional vectors and exact cosine search. Use the query prefix for requests only. Put purpose, object and distinguishing behavior first because the installed encoder configuration caps input at 64 tokens. Index identifiers and the full searchable text separately with BM25. Store revision, label hash and encoder/configuration hash for reproducible reindexing. Filter known incompatibilities by target and framework. Other requirements may need companion bricks. Keep type, dependency, scope and side-effect checks explicit during assembly. Compare BM25, vector search and reciprocal-rank fusion on the same candidates. At 5,000 single-card entries raw float vectors take about 7.7 MB. [Encoder model card](https://huggingface.co/BAAI/bge-small-en-v1.5)

## Picker decision and evaluation

Use the same saved first-pass request, top eight candidate cards per role, compatibility rules, assembler, edit instructions and budgets across picker arms. First check whether retrieval includes a suitable candidate in those eight. Accept equivalent assemblies through independent behavior tests and evidence of required structure.

1. **Baseline.** Use hybrid retrieval and deterministic dependency/port selection, with explicit unfilled roles.
2. **Local model challenger.** Try Qwen2.5-Coder-1.5B-Instruct, already acquired in the earlier model comparison. Constrain its choices to supplied brick IDs, parameter bindings, connections and `missing`. Let the assembler enforce those choices and order placements. Use the original instruction checkpoint. Its earlier English-to-JSON scores concern a different task. [Model card](https://huggingface.co/Qwen/Qwen2.5-Coder-1.5B-Instruct) · [Pinned local checkpoint](../archive/interpretation_diagnostics/n32/README.md)
3. **Reference comparisons.** Compare Big Pickle choosing from the same shortlist with Big Pickle writing the program directly. Charge each arm for all model calls, tool responses, edits and retries it actually uses. Attribute first-pass tokens to every arm using that pass even when the output is replayed for comparability.

After the source audit, select development programs supported by the available material. Before tuning, lock a separate acceptance set with unfamiliar combinations, paraphrases, close substitutes and requests with missing bricks. Keep its text out of card labels, training pairs and acquisition queries. Measure required-role recall at eight, incompatible choices, coverage before editing, build and behavior after editing, block code replaced in the edit, total model tokens and elapsed time. Record failures and budget expirations. Prefer the simplest picker matching the best held-out pass count and wrong-selection rate. Use paired edit effort and latency to break ties. A local model earns its place by rescuing recurring selection or connection errors when the correct bricks were already retrieved. Learn from verified plans only after that failure mode is demonstrated. The installed embedding smoke check establishes that the native encoder works on the host. Comparative picker performance is open.
